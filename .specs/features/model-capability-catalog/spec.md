# Model capability catalog specification

## Problem statement

NexoRoute routes model aliases without knowing whether a target accepts the
request's modalities or tools. Operators also lack a versioned source for model
limits, prices, cache rates, and published performance information.

## Goals

- [x] Ship an auditable, embedded YAML catalog for the initial providers.
- [x] Detect chat request requirements and route only to compatible targets.
- [x] Expose model capabilities and commercial metadata through the model API.
- [x] Preserve compatibility for private and newly released model IDs.

## Out of scope

| Feature | Reason |
| --- | --- |
| Provider benchmarks generated by NexoRoute | Requires a controlled benchmark service and representative regions. |
| Image, speech, transcription, and file-upload endpoints | The current public API exposes Chat Completions only. |
| Automatic catalog downloads | The customer data plane must remain deterministic and independent of a hosted control plane. |

## User stories

### P1: Capability-safe routing

As an operator, I want NexoRoute to avoid targets that can't satisfy a request
so that media or tool content is never silently discarded.

**Acceptance criteria**:

1. WHEN a request includes text, images, audio, documents, tools, or streaming
   THEN NexoRoute SHALL derive the corresponding requirements.
2. WHEN a known target lacks a required capability THEN NexoRoute SHALL skip it
   before making an upstream request.
3. WHEN no known target satisfies the request THEN NexoRoute SHALL return a
   structured `unsupported_capability` error.
4. WHEN a target isn't present in the catalog and unknown models are allowed
   THEN NexoRoute SHALL preserve the existing passthrough behavior.

### P1: Auditable model metadata

As an operator, I want provider and model facts in versioned YAML so that I can
review the sources and understand when the data was checked.

**Acceptance criteria**:

1. WHEN the binary starts THEN it SHALL validate and load all embedded catalogs.
2. WHEN a catalog records pricing THEN it SHALL identify currency and billing
   unit, including cache reads or writes when the provider publishes them.
3. WHEN comparable latency or throughput isn't published THEN the catalog SHALL
   represent the value as unknown instead of estimating it.
4. WHEN a catalog fact can change THEN the catalog SHALL record a retrieval date
   and official source URL.

### P2: Capability discovery

As an API client, I want model details returned by the Models API so that I can
select a compatible alias before sending a request.

**Acceptance criteria**:

1. WHEN a configured alias has cataloged targets THEN `GET /v1/models/{id}`
   SHALL include target metadata and effective gateway capabilities.
2. WHEN aliases are listed THEN existing OpenAI-compatible fields SHALL remain
   available.

## Edge cases

- Unknown content-part types are requirements the gateway can't safely satisfy.
- Azure deployment names and Bedrock inference-profile IDs can map to a separate
  catalog model ID.
- Different targets behind one alias can expose different capabilities.
- Provider prices that vary by region or deployment aren't collapsed into a
  misleading global number.
